## 零、总览

### 0.1 关键数字(决定方案形状)

| 项目 | 数值 | 说明 |
|---|---|---|
| 雷达帧周期 | **114.8 ms(8.7 帧/秒)** | DMA 1798B(满才重启) ÷ 15,666.7 B/s |
| 诊断帧长 | **57 B** | 帧头2 + ver1 + seq1 + 26×int16(52) + 校验1 |
| 平均吞吐需求 | **496 B/s** | 57B × 8.7 帧/秒 |
| HC-05 @115200 实测吞吐 | **~7.3 KB/s**(上限 11.25) | 见设计文档 §2 |
| 带宽占用 | **~6.8%** | 余量充足,可全速(rate 1) |
| 每帧主循环阻塞 | **4.9 ms** | 57B × 86.8µs(115200),仅占帧周期 4.3% |
| 新增 DMA | **不需要** | 115200 阻塞发送已足够 |

> **帧周期修正(2026-09-19)**:此前记为 78.0 ms(12.8 帧/秒),是把"串口按 230400 bps 打满"误当成实际字节率。
> 实际:DMA 是**缓冲满 1798B 才拷贝重启**([DMA.c:78-86](../HARDWARE/DMA/DMA.c#L78-L86)),而 LD14P 点速率恒为 4000 点/秒
> → 每包 47B 装 12 点 → **15,666.7 B/s** → 1798 ÷ 15666.7 = **114.8 ms = 8.7 帧/秒**。
> 影响:帧率与吞吐按 114.8 ms 重算,**方案形状不变(不需要 DMA 的结论反而更稳)**,但报告里的时间轴必须用 114.8 ms
> (上位机 `robocup_telemetry.py` 已按此修正:`DMA_BUF_LEN / LD_BYTES_PER_S`)。

**核心结论**:升到 115200 后,26 个量每帧全发现在**不需要 DMA、不需要黑匣子、不需要降频**,主循环只多花 4.9ms。

## 一、阶段 0:HC-05 升级 115200(硬件,一次性)

> 目的:把 HC-05 的 UART 波特率从 9600 改成 115200。**配置存在模块 Flash,断电不丢,只做一次。**
> ⚠️ 这一步**必须在 USB-TTL 上做,不能接在车上做**(车上 MCU 仍按 9600 发,AT 模式下模块也不理会蓝牙链路)。

### 步骤

| 步 | 操作 | 预期 |
|---|---|---|
| 1 | HC-05 接线到 USB-TTL:RXD→TXD、TXD→RXD、VCC→5V、GND→GND | — |
| 2 | **KEY/EN 脚接高电平(VCC)**;没有 KEY 引脚的模块用按键:**按住按键再上电** | 模块指示灯慢闪(约 2 秒一次)= 进入 AT 模式 |
| 3 | 串口助手打开 USB-TTL 对应 COM 口,**波特率 38400**、8N1、勾选"发送新行(CRLF)" | — |
| 4 | 发 `AT` | 回 `OK` |
| 5 | 发 `AT+UART?` | 回 `+UART:9600,0,0`(记录原值) |
| 6 | 发 `AT+UART=115200,0,0` | 回 `OK` |
| 7 | 发 `AT+UART?` | 回 `+UART:115200,0,0` ✓ |
| 8 | 断电 → KEY 恢复低电平(悬空或接地)→ 重新上电 | 指示灯快闪 = 正常工作模式 |

### 排错与回退

| 现象 | 处理 |
|---|---|
| 发 `AT` 无回显 | ①KEY 必须**上电前**已拉高;②TX/RX 是否交叉;③串口助手是否 **38400** + 新行;④模块是否供电不足(用 5V 而非 3.3V 不稳时) |
| 模块固件不支持 115200(极少数 clone) | 回退第 6 步为 `AT+UART=9600,0,0`,改走**方案 B**:`bsp_bluetooth.c` 保持 9600,`rate` 默认改 2 —— 协议与上位机**完全不变** |
| 想彻底回退 | 重做阶段 0,第 6 步发 `AT+UART=9600,0,0`;代码里 `bsp_bluetooth.c:156` 改回 `9600` |
| PC 端虚拟 COM 的波特率属性 | **一般不影响**(蓝牙 SPP 不是物理串口,PC 侧设置通常被忽略)。若配对后收不到数据,再把 PC 侧属性也改成 115200 试一次 |

### 验证(进入阶段 1 的门槛)

改代码烧录后,PC 用串口助手连蓝牙,应看到**上电即有的 ASCII 输出**(如 `Bluetooth_Init succeed!` 之类行为与以前一致),且 `tele 2` 后出现 `AA 55` 开头的字节流。**若是乱码 → 波特率不匹配,回到阶段 0 排查。**

## 二、车端实现

### 2.1 新文件 `HARDWARE/hc-05/ble_diag.h`

```c
/**
 * @file    ble_diag.h
 * @brief   诊断遥测模块: 26 个控制量 → 57B 定长帧 → 蓝牙回传
 *
 * 帧格式(定长 57B):
 *   [0]=0xAA [1]=0x55 [2]=ver(0x01) [3]=seq
 *   [4..55]  26 × int16 小端(定标见 DiagField 表)
 *   [56]     校验和 = byte[4..55] 累加 & 0xFF
 *
 * 命令: tele 0/1/2 (关闭/旧VOFA+格式/诊断流), rate n (每 n 帧发一次)
 * 设计依据见《诊断遥测方案.md》, 实施步骤见《诊断遥测实施方案.md》
 */
#ifndef __BLE_DIAG_H
#define __BLE_DIAG_H

#include "stm32f4xx.h"

#define DIAG_VER          0x01
#define DIAG_FIELD_N      26                                  /* 字段数 */
#define DIAG_FRAME_LEN    (4 + DIAG_FIELD_N * 2 + 1)          /* = 57 */

void    Diag_Init(void);
void    Diag_Tick(float servo_pwm, uint16_t pid_select, uint16_t danbian_flag);
uint8_t Diag_Command(char *line);     /* 返回 1 = 已处理(供 ble_tune.c 挂接) */

#endif
```

### 2.2 新文件 `HARDWARE/hc-05/ble_diag.c`

**关键设计:字段表驱动(加字段 = 加一行)**

```c
/* 数据源类型 */
#define T_F32  0
#define T_U16  1

typedef struct {
    const char *name;   /* 字段名(CSV 列名) */
    const void *src;    /* 数据源指针 */
    uint8_t     type;   /* T_F32 / T_U16 */
    uint8_t     scale;  /* 存值 = 实际值 × 10^scale */
    float       clamp;  /* 钳位上限, 单位 = 【实际值】(在 ×10^scale 之前施加), 0=不钳位 */
} DiagField_t;

/* ===== 传参缓存(3 个 main() 局部量, 供字段表统一取指针) ===== */
static float    s_servo_pwm;
```

**取数与发送流程**

```c
static uint8_t  s_tele_mode = 1;   /* 默认 1 = 保持现有 VOFA+ 行为 */
static uint8_t  s_rate      = 1;   /* 每 n 帧发一次 */
static uint8_t  s_rate_cnt  = 0;
static uint8_t  s_seq       = 0;
static uint8_t  s_frame[DIAG_FRAME_LEN];
static const float diag_pow10[4] = {1.0f, 10.0f, 100.0f, 1000.0f};

void Diag_Tick(float servo_pwm, uint16_t pid_select, uint16_t danbian_flag)
{
    float v, sv;
    int16_t iv;
    uint8_t i, sum = 0;

    /* ① 缓存传参(字段表统一从静态缓存取) */
    s_servo_pwm    = servo_pwm;
    s_pid_select   = pid_select;
    s_danbian_flag = danbian_flag;

    /* ② 模式 1 / 未连接: 走原有 VOFA+ 通道, 零改动 */
    if (s_tele_mode != 2) { BLE_Tune_Telemetry(Servo_pd.err, servo_pwm, pid_select); return; }

    /* ③ 降频(默认 rate=1 全速; 出问题时用 rate 2~10 观察) */
    if (++s_rate_cnt < s_rate) return;
    s_rate_cnt = 0;

    /* ④ 组帧 */
    s_frame[0] = 0xAA;  s_frame[1] = 0x55;
    s_frame[2] = DIAG_VER;  s_frame[3] = ++s_seq;
    for (i = 0; i < DIAG_FIELD_N; i++) {
        switch (diag_tab[i].type) {
            case T_F32: sv = *(const float *)diag_tab[i].src;               break;
            default:    sv = (float)(*(const uint16_t *)diag_tab[i].src);   break;
        }
        /* ⚠ 钳位必须在定标【之前】: 表里的 clamp 是【实际值】上限, 与 scale 无关。
         * 顺序写反(先 ×10^scale 再比 clamp)会把上限缩小 10^scale 倍:
         *   err  ±600  实际只到 ±60   → 算法 ±500 的饱和/过冲全被削平
         *   k    ±30.0 实际只到 ±0.03 → k 工作区到 ±0.35, 曲线被压成一条直线
         * 详见 §7.5 */
        if (diag_tab[i].clamp > 0) {
            if (sv >  diag_tab[i].clamp) sv =  diag_tab[i].clamp;
            if (sv < -diag_tab[i].clamp) sv = -diag_tab[i].clamp;
        }
        v = sv * diag_pow10[diag_tab[i].scale];            /* 定标 */
        if (v >  32767.0f) v =  32767.0f;                  /* 定标后 int16 边界防御 */
        if (v < -32768.0f) v = -32768.0f;
        iv = (int16_t)(v + (v >= 0 ? 0.5f : -0.5f));       /* 四舍五入 */
        s_frame[4 + 2 * i] = (uint8_t)(iv & 0xFF);
        s_frame[5 + 2 * i] = (uint8_t)((iv >> 8) & 0xFF);
    }
    for (i = 4; i < DIAG_FRAME_LEN - 1; i++) sum += s_frame[i];
    s_frame[DIAG_FRAME_LEN - 1] = sum;

    /* ⑤ 发送: 57B × 86.8µs = 4.9ms 主循环阻塞(115200) */
    for (i = 0; i < DIAG_FRAME_LEN; i++) BLE_Send_Bit(s_frame[i]);
}
```

### 3.3 帧解析器(核心,决定数据可信度)

```
输入: 原始字节流
循环:
  在缓冲区里搜 "AA 55"
  命中 → 取其后 57B → 检查 ver==0x01 且校验和一致
        成功: 解析 26 个 int16 → 除以 10^scale → 一行数据; 用 seq 算丢帧
        失败: 前移 1 字节继续搜(校验失败计数 +1)
  未命中 → 前移 1 字节
```

- **丢帧率** = Σ(seq 跳变 - 1) / 总帧数 —— 这是判断"115200 稳不稳"的客观指标
- ASCII 回复(`OK kp=450`)会自然被跳过并单独提取为**事件行**(记录改参时刻,便于对照)

### 3.4 判读项(10 项)与算法

| # | 判读项 | 算法要点 |
|---|---|---|
| 1 | 链路质量 | 总帧数、丢帧率、校验失败帧数、实际字节速率、`get` 干扰段数 |
| 2 | **模式分布** | `pid_select` 值计数 → 各模式占比 + 切换次数 + 模式时间线 |
| 3 | **err 饱和率** | 分模式统计 \|err\|≥490 占比;err 直方图(按模式分组) |
| 4 | **弯道 k 分布** | 模式 3/4/8/9 的 `Forward.k` 直方图 → 验证 A 改动 0.35 分档 |
| 5 | **方向异常** | 连续 ≥3 帧 (模式∈{3,8} 且 err>0) 或 (∈{4,9} 且 err<0) |
| 6 | **出弯反踢** | 模式 {1,2,3,4,8,9}→{0,5} 帧的 Δerr/Δpwm 超阈值 |
| 6b | **PWM 猛甩** | **全场**单帧 ΔPWM(不限模式切换)>100 / >250 的帧数 + Top-5 明细表(帧号、ΔPWM、模式变化、err 变化)——抓"舵机突然甩一下" |
| 7 | **强制打满残留** | `state_left/right_cnt > 0` 的帧占比、位置、期间的 err 陈旧情况 |
| 8 | 断点抖动 | `duandian` 相邻帧跳变 >150mm 的次数与位置 |
| 9 | 速度环 | `Speed_now` vs `Speed_mubiao`:均值/标准差/超调 + 对 **5 帧滑动平均后**数过零(不平滑的话噪声会让每帧翻号,测不出真振荡) |
| 10 | **可疑片段清单** | 上述异常按"窗口内异常帧密度"打分 → **Top-5 片段**(帧号/时间/原因/关键量) |

> 第 6b 项是最有用的一项:`0→0`(模式没变)却 ΔPWM=352 这种行,一眼就能定位到"强制打满残留退出时舵机猛甩"。

### 7.2 字段速查

见 §2.2 的字段表(顺序 = 帧内顺序 = CSV 列顺序),定标换算:`实际值 = 存值 / 10^scale`。

### 7.3 三条语义陷阱(解读报告前必读)

1. **err 有陈旧时刻**:直道模式 0 且 `|Midline.k| ≤ 0.1` 时保持舵机、不调 PD,`err` 保持上帧值;强制打满残留生效时同理
2. **`pid_select = 0` 有三种含义**:真直道 / 强制打满残留中 / 本帧被跳过 —— 靠 `state_*_cnt` 与 `valid_couter` 区分
3. **`Midline.k/b` 来源随模式变**:模式 0/5/7 = 中线拟合;模式 1/2 = 墙拟合;模式 3/4/8/9 不更新(用 `Forward.k`)

### 7.4 与设计文档的差异(本次更新)

| 项 | 设计文档初版 | 本实施方案(方案 A 定稿) |
|---|---|---|
| 波特率 | 9600(可选升级) | **115200(已定)** |
| 发送方式 | 阶段 1 阻塞降频 → 阶段 5 DMA | **阻塞全速(4.9ms,占 6%)**,DMA 取消 |
| 默认 rate | 2 | **1** |
| 黑匣子 | 后备 | **不做**(带宽充裕) |
| 点云回传 | 未提 | 列为可选阶段 6 |

### 7.5 定标/钳位顺序(2026-09-19 修正)

**原示例编码的错误**:先 `v = sv × 10^scale` 定标,再拿 `clamp` 去比 `v` —— 而 `clamp` 是**实际值**上限。等于实际生效的上限被缩小了 `10^scale` 倍:

| 字段 | scale | 表里写的钳位(实际值) | 代码实际生效(实际值) | 后果 |
|---|---|---|---|---|
| `err` | 1 | ±600 | **±60** | 算法限幅 ±500,饱和与过冲**全被削平**;上位机 `ERR_SAT=490` 永不触发 |
| `Midline.k` / `Forward.k` / `Forward_2.k` / `Forward_3.k` | 3 | ±30.0 | **±0.03** | k 工作区到 ±0.35,曲线被压成 0.03 一条直线,拟合质量类结论全部无效 |
| `Midline.b` / `Forward.b` | 0 | ±30000 | ±30000 ✓ | scale=0,不受影响 |
| 其余 21 个 | — | clamp=0 | 不钳位 ✓ | 不受影响 |

**危险之处**:5 个最有诊断价值的连续量全部中招,而且**不溢出、不报错** —— 是静默削平。表格化统计只会看到"err 最大 60""k 恒为 0.03",很容易被误读成"车跑得很稳",直接误导后续调参。

**修正**:钳位提前到定标之前,钳的是 `sv`(实际值)。这样 `clamp` 的含义与《诊断遥测方案.md》§4.4 一致,且与 `scale` **彻底解耦** —— 以后给任何字段配 scale 都不会再触发。

**一致性检查**:上位机模拟器 [robocup_telemetry.py:759](上位机/robocup_telemetry.py#L759) 是 `vals[name] × 10^scale` + int16 边界钳位,**没有字段级钳位**;其模拟值都在字段 clamp 之内,所以**修正后两者才语义一致**。修正前模拟器发 k=500(→0.5)、实车发 30(→0.03),同一个 CSV 里两套数。
