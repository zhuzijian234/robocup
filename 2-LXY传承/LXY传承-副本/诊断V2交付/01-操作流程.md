# 遥测V2操作流程

日期：2026-09-20。适用：LXY传承-副本。协议布局：`rc26-mask31-v2.1`。

当前交付为已实现、可编译及可进行台架验收的版本。尚未连接实车、未烧录；不把软件测试当作蓝牙/雷达实测。

## 1. 烧录前

1. 保存当前能跑的固件及参数。正常循线仍使用LD14P，雷达USART2仍为230400；不要把雷达串口与蓝牙串口混淆。
2. 新固件蓝牙USART6默认 **115200、8N1**。HC-05模块的实际数据模式UART也必须匹配；Windows虚拟串口选115200并不能代替修改模块UART配置。
3. 若模块仍是9600，按实际模块/底板说明书进入AT配置，查询并保存旧配置，设置数据UART为115200/8N1，再查询确认。不同底板的KEY、EN、电源与逻辑电平可能不同，本说明不提供通用接线或保证通用AT指令。
4. 如暂时不能配置模块，可在ble_diag.h把BLE_UART_BAUD改为9600，重建并在主机选择9600；V2需降频、重新验收总吞吐，不能照搬115200的性能结论。首选115200。
5. 主工程入口为USER/Template.uvprojx，两份EIDE已登记新增文件。TIM6被诊断时钟独占，TIM5仍负责速度环与雷达失效保护。启动栈由1KiB增加至4KiB。
6. 从项目目录运行 `python -B test/update_diag_build_id.py`，更新构建标识和源码清单，然后全量编译。再次改源文件后必须重做这一步。
7. 架空驱动轮再首次烧录。保持此前失效策略：启动无有效处理时PWM为0；运行后约500ms无有效处理则锁定PWM为0，恢复雷达不会自动起步，需要重启。PWM归零不是主动制动。

## 2. 推荐：命令行完整采集

在“上位机”目录打开终端，使用安装了numpy、matplotlib、pyserial的Python环境。

```powershell
python -B robocup_telemetry.py list
python -B robocup_telemetry.py capture-v2 --port COM5 --baud 115200 --rate 1 --sec 30 --out log/ld14p_baseline.bin
python -B robocup_telemetry.py report log/ld14p_baseline.bin
```

COM5需替换成实际端口。程序自动执行：

`info → session 非零随机数 → tele 3 → rate 1 → getcfg → 完整配置确认 → 正式采集`

每一步必须收到对应ACK；协议、布局、配置不完整或超时则失败并保留已有记录。不是“发出命令就算成功”。协商期间字节也保存，meta中的pre_roll_s标明正式采集起点。协商前的旧流可能出现，报告不把它计入正式CONTROL区间。

运行中3秒没有任何串口输入会以“链路或设备无响应”结束；不能仅凭此判定雷达坏了。检测到设备session改变则结束本次run，重新采集必须重新协商。若新参数revision缺配置，会请求getcfg，并在报告中保留未知配置区间。

Ctrl+C可停止并保存文件。不要同时用VOFA、串口助手或另一个程序打开同一COM口。

## 3. GUI操作

1. 启动原上位机，选择串口及115200并连接。
2. 选择采集时长，点“一键诊断”。GUI释放原串口，后台进程独占串口完成协商、采集、保存、报告，避免绘图和报告堵塞读取。
3. 此流程暂不显示实时曲线；点“停止”会请求后台保存并退出，不直接杀进程。
4. 等任务结束后查看报告。下一次任务需要重新连接。不要直接关闭窗口来代替停止，后台保存尚未结束时关闭可能造成不完整日志。

普通“开始采集”保留旧功能，不能替代完整V2协商；旧固件选9600普通采集，再用vofa子命令分析。未经协商的V2日志可以解析，但缺失配置会被明确标注。

## 4. 需要交给AI的文件

假设输出名为run.bin：

| 文件 | 用途 |
|---|---|
| run.bin | 原始接收字节，包含协商阶段 |
| run.bin.rx.jsonl | 每块偏移、长度、相对时间及host_monotonic_ns |
| run.bin.meta.json | SHA256、实际字节数、时长、run UUID、session、协议、配置、命令、起止UTC及结束原因 |
| run.csv | CONTROL字段、有效/更新/限幅位、动作、设备时间等 |
| run.events.jsonl | HEALTH、CONFIG分片、EVENT及未知类型记录 |
| run_report.md、run.png | 摘要及采样点图 |
| source_manifest.json | 本次固件构建标识对应的源码摘要；应在改源码前随run另存 |

前三份文件必须一起保留。修改bin或丢失时间记录时，解析器会拒绝不匹配的元数据。报告给出“线索”，不根据少量摘要自动调整控制增益或烧录。

## 5. 手工查询和兼容命令

所有命令以换行结束，逐条发送并确认，不批量粘贴大量命令：

```text
info
session 12345
tele 3
rate 1
getcfg
radar
tele 0
```

- tele0关闭主动遥测；在途完整帧允许收尾，仍能响应查询。tele1为36B JustFloat；tele2为57B V1；tele3为V2，互斥。
- rate1～10指每N次控制结果抽样一次，不是Hz；HEALTH不随rate降低。
- get保留原整数回显，**不是精确配置备份**；getcfg用float32原始位记录参数，例如kp3=0.0395不会被get的整数显示精度替代。
- 参数名、单位保持原样。参数组不是原子事务，必须逐条确认；配置分片发送期间写参数会得到ERR busy，待配置完成再重试。
- radar现在是一条完整文本消息，包含calls/sync/short/missing/raw/invalid/age10ms/start/stop/timeouts；不代表CRC校验统计。
- 模块STATE断连后清理未发队列，session变为0；重连必须重新协商。

## 6. 常见现象

- 没有INFO：先确认模块UART和固件波特率匹配、串口未被占用、是否仍是旧固件。不要直接调雷达PWM或改串口2。
- 有HEALTH、没有CONTROL：检查input_seq是否增长、age状态、解析失败及失效保护；没有新输入时不会重复旧CONTROL。
- stop=1：说明既有失效保护已锁定电机；遥测命令不会解除它。
- tx_drop增长：发送队列拥塞或会话切换清队列；优先降rate、停止高频查询，并检查无线链路。队列发完不等于PC已收到。
- unsupported_mask非零：相应HEALTH项目未实现，不能把占位0解释成“零错误”。
