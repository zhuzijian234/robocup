# 诊断扩展：转向、编码器与雷达输入

日期：2026-09-22。针对 19:41 记录中的速度异常、转向跳变、雷达转速异常增加观测。

## 1. 已增加的数据

| 需要回答的问题 | 新增证据 | 采样方式 |
|---|---|---|
| 编码器是否将反向计数解释成巨大正数 | TIM4 原始 uint16 计数、上位机 int16 解释、不经 int16 缩放的实际 Speed_now | TIM5 每次控制中断留样，约 100 Hz |

| 日志是否漏数据 | 输入覆盖计数、发送丢弃计数、MOTOR环形缓存丢样计数、采样序号、DETAIL匹配缺失数量 | 随诊断帧发送并进入报告 |

已有 CONTROL 的 servo_pwm 是 TIM3 CCR1 最终位置指令，仍保留。它可经标定换算成目标角度，但不是舵机实际角度反馈；也不能直接表示扭矩。当前没有可读取的舵机角度、电池电压、舵机/驱动电流接口，未伪造这些测量值。若需要判断实际到位速度或卡滞，请增加反馈传感器，或同步拍摄车轮转动录像。

本轮只增加诊断采样。编码器符号处理、PD公式/增益、雷达包是否参与控制的决定仍按现役代码执行。CRC统计是观察结果，尚未据此拒收坏包。

## 2. 使用流程

1. 用当前源码重新全量编译、烧录，再复位。更新上位机使用同目录的新版 Python 文件。
2. 串口选 HC-05 对应 COM，波特率 115200。使用 GUI 的“一键诊断”，建议 30 秒，rate=1。普通 VOFA 采集没有这些扩展帧。
3. CLI 的用法不变：

```powershell
& 'D:\anaconda3\anaconda3\python.exe' .\robocup_telemetry.py capture-v2 --port COM4 --baud 115200 --rate 1 --sec 30 --out log\diagnostic.bin
& 'D:\anaconda3\anaconda3\python.exe' .\robocup_telemetry.py report log\diagnostic.bin
```

以上命令在项目“上位机”目录执行，COM4替换成实际端口。

4. 握手的 INFO 将包含 `detail=1 motor=1`。没有这两个标记通常意味着车端仍是旧固件；旧文件依然可以解析，但无法补出历史缺失数据。
5. 采集结束会新增 `diagnostic.detail.csv`、`diagnostic.motor.csv`，原 `.bin`、`.bin.meta.json`、`.bin.rx.jsonl`、`.csv`、`.events.jsonl`、报告和图仍保留。
6. 请提供同一前缀的整个文件组，并说明：架空还是落地、是否手推/倒推、左右哪个弯有问题、何时停车/碰撞/人工拿起。录像可帮助判断目标指令与真实动作的差别。

GUI 无需另外勾选字段：V2会话建立后自动启用扩展。图仍为原 CONTROL 图；扩展明细保存在两个 CSV 和事件 JSONL 中，摘要在报告的“扩展诊断”段。

## 3. 兼容性和队列预算

- 协议仍为 V2，原 layout `rc26-mask31-v2.1`、CONTROL108B、HEALTH80B 不变。新增 type=5 DETAIL、type=6 MOTOR，各自带 schema=1。旧上位机可跳过未知类型；新版同时支持旧固件和旧日志。
- DETAIL 176B，与 CONTROL 按 `(session, control_seq, param_revision)` 对应。独立入队，拥塞时可能只有其中一帧收到；报告明确统计未匹配 CONTROL，不用最近一帧误配。
- MOTOR 每样本28B，每帧最多8个，帧长 `32+28N`，最大256B。样本不足8个时最老样本等待达到80ms才尝试入队；主循环忙时会晚于80ms发送。
- MOTOR缓存64个样本，约0.64秒；ISR只留样，不发送串口，不计算CRC。主循环批量入原发送队列，队列仍是4个普通槽+2个关键保留槽。满时不等待：环形缓存满丢新样本并计数；DETAIL/CONTROL入队失败沿用tx_drop。
- 同一MOTOR包内revision相同、样本序号连续；跨参数变更或丢样位置拆包。每次session/tele命令丢弃尚未入队的旧环形样本，此类人为切换不计缓存溢出。采集结束可能有约80ms及队列排队中的尾部数据尚未到达，不能当作采集已覆盖全部控制周期。
- 按100Hz MOTOR且8样本/包估算约3200B/s；CONTROL+DETAIL合计每次284B，HEALTH约80B/s。8.71次/s时合计约5754B/s（115200/8N1线速的50%）；12次/s约6688B/s（58%）；20次/s压力预算约8960B/s（78%）。未含CONFIG/EVENT突发、小包开销及蓝牙实际链路限制。
- rate>1只降低CONTROL/DETAIL频率，MOTOR仍逐次TIM5留样。当前推荐rate=1；不能把线速预算当作HC-05实测能力。上车须确认丢样和处理周期没有显著恶化。
- MOTOR与控制算法诊断部分不依赖雷达型号；换M10仍可复用。CRC、47字节包、VerLen、角度覆盖等输入摘要目前由LD14P解析器填充，M10必须接入自己的解析器和语义，不能沿用LD14P CRC或谎报已支持。

## 4. 线协议登记

均使用既有14B公共头、末尾2B CRC16。下列偏移为payload内偏移；整数小端，float为IEEE754 float32，不做int16定标。NaN/Inf保留为诊断证据，计算统计前检查有限性。

### DETAIL：type=5，总长176B

payload前96B为24个u32，按以下顺序：

```text
schema control_seq param_revision input_seq detail_flags process_us
previous_mode ref_start ref_end ref_count center_count hold_count
radar_packets radar_crc_bad radar_verlen_bad radar_angle_bad
radar_header_missing radar_sync_offset radar_angle_bins
radar_sync_fail_total radar_missing_total input_drop_total tx_drop_total motor_drop_total
```

payload偏移96起为16个float32，按以下顺序：

```text
pd_err_previous pd_err pd_p pd_d pd_kp pd_kd pwm_unclamped pwm_mid
ref_x ref_y ref_dy pd_line_k pd_line_b pd_err_before_reset center_mean width_candidate
```

`detail_flags`：

| bit | 含义 |
|---|---|
| 0 | 本次执行PD；pd_*、pwm_unclamped、pwm_mid和previous_mode可用 |
| 1 | 模式1/2选中了参考点；ref_x/y/dy可用 |
| 2 | 本次进入PD时将历史误差清零 |
| 3 | 模式1/2未选中任何参考点，仍执行了现役公式 |
| 4 | 本次PD的限幅前PWM超出1170～1720 |
| 5 | 解析期间观察到输入块被更新，现役main丢弃本次解析结果 |
| 6 | 本次调用了LD14P解析器，雷达摘要可用 |
| 7 | 本次计算过中线点数，center_count可用 |
| 8 | 本次模式6/7使用了center_mean |

其他位保留0。未置有效标志的字段填0仅作占位，不表示真实测量为0。

- `ref_start/end`来自实际PD实参，end不包含；`ref_count=max(end-start,0)`，不是整个边界总点数。ref坐标单位mm。
- `pd_err_previous`是PD公式实际使用的旧误差；`pd_err_before_reset`是本次PD进入时的旧误差。P/D项均乘10，单位与CCR相同；`pwm_mid`记录实际计算使用的基准（现役uint16截断后为1440），不能用配置名义1445替代。
- `pd_line_k/b`是传入PD的线参数，不表示拟合一定有效，需同时结合CONTROL的拟合有效位。
- `width_candidate`在感知有效的主循环末尾记录本次宽度候选；无效动作不使用。`hold_count`是连续控制次数，非毫秒，即使rate>1也按实际控制次数累计。
- `radar_packets`仅计现役解析器选中的0x54候选包。CRC算法按LD14P开发手册表：poly=0x4d、init=0、非反射，覆盖前46B；VerLen期望0x2c；起止角度必须小于36000。三类错误可能重叠，不能简单相加当作坏包总数。
- `radar_sync_offset=0xffffffff`表示该块未找到同步；其他值为字节偏移。这是偏移字段的专用哨兵，与设备时间无关。
- `radar_angle_bins`的bit0～11分别表示解析后非零距离槽是否覆盖[0,30)、[30,60)…[330,360)度；坐标沿用现役变换。它包含尚未按CRC拒收的数据，不等价于可信完整扫描。
- `process_us`从本次Diag_Begin到Diag_Submit入口，含被中断抢占时间，不含本次遥测编码/入队耗时。control_dt包含相邻控制提交之间的整体开销。

### MOTOR：type=6，总长32+28N

payload前16B：schema u16、count u16、first_sample_seq u32、param_revision u32、motor_dropped u32。

其后N个样本，每样本28B：

| 偏移 | 类型 | 字段 |
|---:|---|---|
| 0 | u32 | sample_us：设备快照微秒，约71.6分钟回绕 |
| 4 | u16 | encoder_raw：TIM4计数器读取值 |
| 6 | u16 | motor_pwm：TIM2 CCR1最终值 |
| 8 | f32 | speed_float：未被遥测int16限幅的Speed_now |
| 12 | f32 | target_float：同一次ISR的目标速度 |
| 16 | f32 | motor_integral：PI累加误差限幅后的积分状态 |
| 20 | f32 | motor_prelimit：限制到0～100之前的电机控制输出 |
| 24 | u32 | motor_flags |

motor_flags：bit0本次读取编码器；bit1本次执行PI（integral/prelimit有效）；bit2 Radar_started；bit3锁停；bit4倒车分支。其他位0。倒车分支可能未读编码器，必须检查bit0；锁停/启动抑制分支不执行PI，不能使用旧PI值作为本次计算证据。

sample_seq为first+i的u32模加。上位机附加encoder_signed是encoder_raw的int16解释，用来发现反向计数风险，并未修改车端测速。时间差用u32模减，跨session不作连续计算。sample_us为ISR末段留样时刻，不是编码器脉冲逐个发生的时间。

## 5. 上车测试和验收

1. 架空并固定车辆，确认测试不会意外驶出；先记录静止，再按已知方向轻转轮子，核对原始计数、int16解释与真实方向。不要仅看到负数就认定接线错误。
2. 保持现场场景，采30秒。报告应出现DETAIL和MOTOR；检查未匹配CONTROL、motor_sequence_gaps及累计motor_drop/tx_drop变化。首尾包边界不用于估算完整100Hz采样时长。
3. 对一次PWM跳变，按session/control_seq/revision找到DETAIL，核对`pwm_mid+pd_p+pd_d`与`pwm_unclamped`，再与CONTROL最终CCR比较（允许float运算及整数截断差异）。
4. 人为让参考边界缺失，确认空参考标志出现；本轮未修复控制算法，不把“标志出现”当作控制已安全处理。
5. 编码器异常发生时，检查同一MOTOR样本的raw、signed、speed_float、PI积分、限幅前输出与CCR。能区分“异常测速压低输出”与“仍有输出但无测速”；仍不能仅凭日志区分机械卡住、断电、编码器断线。
6. 核对CRC坏包数、同步偏移和角度覆盖，判断先处理输入问题还是调增益。雷达健康诊断仍有未实现的UART/DMA错误项，不能把HEALTH占位0当作零错误。
7. 复测原控制周期、process_max和发送丢弃。CRC观察及更高串口流量会增加CPU工作量；编译成功不能代替上车时序验收。
