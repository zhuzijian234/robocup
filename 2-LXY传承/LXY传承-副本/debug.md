查了代码，首要原因很明确：硬件测试模式还开着。

主因：HW_TEST_MOTOR_SERVO = 1（main.c 第65行）
看它上面那段注释就懂了（main.c 第60-64行）：

设为1: 每次收到雷达DMA一帧数据后，舵机在[1360,1800]之间往复扫描，同时电机占空比在[10,100]之间往复变化

所以你现在看到的现象——上电后舵机一直左右摇摆、电机转速也在变——正是这个测试模式的预期行为，不是故障。它是之前专门用来测试舵机/电机硬件好坏的。

验证方法：插上串口看打印，如果一直在刷：


Servo_Test PWM: 1580
Moto_Test PWM%: 65
那 100% 就是测试模式在跑。

解决：把第65行改成 0，重新编译烧录。

但改完可能还会摆，还有三个坑要心里有数
1. 测试模式和循线逻辑是同时编译的（第172行 #if HW_TEST_MOTOR_SERVO 和第208行 #if 1 是两段并列代码），两套逻辑每帧都在抢着写舵机（Midline_PD 内部也会直接调 Servo_ChangePwm，CENTRE_LINE.c 第343行）。现在舵机的动作其实是两套命令打架的混叠结果。

2. 车放桌上/地上，周围不是赛道 → 雷达照到的是墙、桌椅、杂物 → 中线/断点数据本来就是乱的 → PD 算出的舵机值自然左一下右一下。这种情况下"摇摆"是正常的，得到赛道上才能判断循线好坏。判断依据：串口刷 k: xxx, b: xxx 就说明循线逻辑在跑，数据是乱的环境所致。

3. main.c 第219行有个 bug：有效点 ≤20 时写的是 break，它跳出的是 while(1) 主循环本身（不是跳过这一帧）——整个控制程序当场死掉，之后只有 TIM5 速度中断还在跑。如果烧 0 版本后串口刷完 DMA_RX_DONE 就没了动静，就是这个 bug 触发了。正确的写法应该是跳过本帧继续循环（比如用 continue 或者把逻辑包进 else）。
