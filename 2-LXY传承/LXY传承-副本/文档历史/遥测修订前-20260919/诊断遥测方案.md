# 诊断遥测方案(蓝牙回传 → 上位机 → 自动判读)

> 目标:把 LXY 10 模式循线算法的**每一个决策依据**逐帧回传到电脑,上位机自动生成分析报告并定位问题。
> 适用工程:`2-LXY传承/LXY传承-副本`
> 撰写日期:2026-09-17

---

> ## ⚠️ 决策更新(2026-09-17):HC-05 升 115200
>
> 本文的带宽分析基于 **9600**。经实测数据核对后**已决定升级 HC-05 到 115200**:
> - HC-05 @115200 实测持续吞吐 **~7.3 KB/s**(上限 11.25),我们的诊断流只要 **496 B/s = 占用 ~6.8%**,余量充足
> - 由此**取消 DMA 阶段**(57B 阻塞仅 4.9ms/帧,占帧周期 4.3%),**取消黑匣子**,`rate` 默认 1(全速)
> - 9600 反而更紧:UART 上限 960B/s,诊断流占 52%,仍需降频到 `rate 2`
>
> **落地步骤、代码骨架、接线点、操作手册见[诊断遥测实施方案.md](诊断遥测实施方案.md)(以此为准)。**

## 一、目标与范围

**要解决的**:现役代码 err 常飙 |500|、模式几乎只有 0~4(8/9 罕见)、有时舵机摆错。已知根因是 1/k 反解构造(A/B/C 三处已改),但**改完效果如何、还剩哪些问题,必须靠实测数据说话**——肉眼盯舵机和 VOFA+ 波形看不出决策链路里哪一步错了。

**要做的**:
1. 车端把每帧的**控制输出 + 全部决策依据**(26 个量)打包回传
2. 上位机接收存盘,自动解析、统计、判读,生成 Markdown 报告 + 图表
3. 我读报告 → 定位问题 → 提修改方案

**不做的**:不改电机控制流程、不改雷达接收、不改舵机驱动、不改现有蓝牙调参命令语义。

## 二、现状实测参数(所有计算的约束)

| 项目 | 实测值 | 来源 |
|---|---|---|
| 雷达帧周期 | **114.8 ms**(8.7 帧/秒) | DMA 缓冲 1798B(满才重启) ÷ 15,666.7 B/s |
| 蓝牙波特率 | **9600** 8N1 | `bsp_bluetooth.c:156` |
| 蓝牙通道容量 | 960 B/s = **110 字节/帧** | 9600 ÷ 10bit ÷ 8.7帧 |
| 单字节发送代价 | **1.04 ms 主循环阻塞** | `BLE_Send_Bit` 死等 TXE(`bsp_bluetooth.c:106-110`) |
| 现有遥测占用 | 7×float32+帧尾 = 32B = 33 ms/帧(29%) | `ble_tune.c` |
| RAM 余量 | 58.2KB / 128KB 已用,**余 ~70KB** | `USER/build/Template/Template.map` |
| DMA 占用 | 仅 **DMA1 Stream5**(雷达 RX) | `HARDWARE/DMA/DMA.c` |
| HC-05 与雷达 | 互不干扰(USART6 vs USART2) | — |

> **帧周期修正(2026-09-19)**:此前记为 78.0 ms(12.8 帧/秒),是把"串口按 230400 bps 打满"误当成了实际字节率。
> 实际:DMA 是**缓冲满 1798B 才拷贝重启**([DMA.c:78-86](../HARDWARE/DMA/DMA.c#L78-L86)),而 LD14P 点速率恒为 4000 点/秒
> → 每包 47B 装 12 点 → 15,666.7 B/s → **1798 ÷ 15666.7 = 114.8 ms = 8.7 帧/秒**。
> 影响:所有时间轴、帧率、带宽余量按 114.8 ms 重算(**方案本身不受影响,余量反而更大**)。

**关键结论**:115ms 的帧周期是硬节拍;要"全面"就必须让每帧的信息量从 7 个 float 提到 26 个量,同时**不能**让发送时间挤爆 115ms。

## 三、传输效率分析:为什么是 int16 定点 + DMA

### 3.1 真正瓶颈是阻塞时间,不是字节数

`BLE_Send_Bit` 是阻塞轮询,**每字节占死主循环 1.04ms**。所以:

```
每帧主循环开销 = 发送字节数 × 1.04ms + 管道处理时间 + printf 调试 (~15-25ms)
```

| 方案 | 帧长 | 主循环阻塞 | 结果 |
|---|---|---|---|
| 现状 7×float32 | 32B | 33 ms | ✓ 现状可用 |
| 26 量 × float32 | 109B | **113 ms** | ✗ 达帧周期 98%,**必掉帧** |
| 26 量 × int16 | 57B | 59 ms | △ 占帧周期 51%,9600 下吃紧,115200 下轻松 |
| 26 量 × int16 + DMA | 57B | **~0 ms** | ✓ 可行,且可全速 |

### 3.2 编码方案对比(同等信息量)

| 方案 | 每值字节 | 26 量体积 | 9600 可行性 | 精度代价 |
|---|---|---|---|---|
| ASCII 文本 | ~7 | ~180B | ✗ 超 2.4× | — |
| float32 | 4 | 109B | ✗ 超预算 | 无 |
| **int16 定点(选定)** | **2** | **57B** | ✓ | **无实际损失**(见 3.3) |
| int8 + 位打包 | ~1.4 | ~40B | ✓ | 距离分辨率降至 16mm;逐字段定标+移位,出错面大 |
| delta + varint | 变长 | ~30B | — | 只对慢变量省;本帧内全是快变量,不省 |

**不选位打包/int8 的理由**:省 30% 字节,但要为 26 个字段各定一套移位规则,一旦错位整帧数据静默错乱;而 int16 已经够用,风险收益不划算。

### 3.3 int16 为什么等于无损

量化步长全部**低于上游传感器/拟合噪声**,即量化误差被噪声淹没:

| 量类 | 定标 | 分辨率 | 上游噪声 |
|---|---|---|---|
| 距离(mm) | ×1 | 1 mm | 雷达 ±10~20mm |
| 斜率 k | ×1000 | 0.001 | 拟合噪声 ≫0.01 |
| err | ×10 | 0.1 | PD 有效分辨率 ≫1 |
| PWM/角度/计数 | ×1 | 整数 | — |

### 3.4 DMA 发送(阶段 3)

- USART6_TX 在 F407 上固定映射 **DMA2 Stream6 + Channel5**(备选 Stream7),项目**完全空闲**
- DMA 后台搬运,主循环零阻塞;硬件自己发完 57B(≈59ms),期间 CPU 继续跑控制
- 配置全部写在新文件里,**不改 `bsp_bluetooth.c`、不改 DMA 模块**
- 完成判断:轮询 `DMA_GetCmdStatus(DMA2_Stream6)`,无需中断

## 四、协议规范

### 4.1 帧格式(定长 57 字节)

| 偏移 | 长度 | 内容 | 说明 |
|---|---|---|---|
| 0 | 1 | `0xAA` | 帧头 1 |
| 1 | 1 | `0x55` | 帧头 2 |
| 2 | 1 | `ver` | 协议版本,当前 `0x01` |
| 3 | 1 | `seq` | 帧序号,每帧 +1(0~255 回绕) |
| 4 | **52** | 26 × int16 | **小端**;顺序与定标见 4.2 |
| 56 | 1 | `sum` | 校验:字节 4~55 累加和 & 0xFF |

- 定长 + 双字节帧头 + 校验:上位机搜 `AA 55` 后按 57B 取帧,校验不过就前移 1 字节重找 → 抗干扰、可自恢复
- `seq` 用于算**丢帧率**;校验失败率单独统计
- int16 溢出防护:车端发送前**按字段钳位**(见 4.4),上位机解析后再做量程校验

### 4.3 定标换算(上位机侧)

```
实际值 = 存值 / 10^scale        # scale: err=1, k=3, 其余=0
```

### 4.4 发送前钳位规则

⚠️ **钳位在定标之前施加,钳的是实际值**(`clamp` 的单位是实际值,与 `scale` 无关);定标之后再按 int16 边界做一次防御性钳位。顺序写反会让上限缩小 `10^scale` 倍(err 变 ±60、k 变 ±0.03),详见《诊断遥测实施方案.md》§7.5。

| 字段 | 钳位 | 理由 |
|---|---|---|
| k 类 | ±30.0(存 ±30000) | 拟合退化时 k 可能爆;int16 上限 32767 |
| b 类 | ±30000 | 同上 |
| 其余 | 按量程表 | 计数类不会溢出,防御性钳位 |

### 4.5 三个必须知道的语义陷阱(否则报告会误读)

1. **`err` 有"陈旧"时刻**:
   - 直道模式 0 且 `|Midline.k| ≤ 0.1` → 直接保持舵机,**不调 Midline_PD,err 不更新**([main.c:445-447](USER/main.c#L445-L447))
   - 强制打满残留生效时(§4.5-2)→ 同上,err 不更新
   - ⇒ 分析"err 与模式不符"的帧时,先看 `state_left/right_cnt` 是否 >0
2. **`pid_select=0` 有三种含义**:真直道 / 强制打满残留中 / 本帧被跳过。要靠 `state_*_cnt` 与 `valid_couter` 区分
3. **`Midline` 来源随模式变**:
   - 模式 0/5/7 → 中线 `LEIDA_DATA_CENTER` 的拟合
   - 模式 1/2 → 左/右**墙**的拟合(main.c 里模式 1 传的确实是 LEFT_Plane)
   - 模式 3/4/8/9 → **不更新**(用的是 `Midline_forward`)

### 4.6 新增蓝牙命令

| 命令 | 作用 | 默认 |
|---|---|---|
| `tele 0` | 关闭遥测 | — |
| `tele 1` | 旧格式(8 通道 VOFA+ JustFloat，末通道=雷达转速) | **默认** |
| `tele 2` | 诊断流(57B 定长帧) | — |
| `rate n` | 每 n 帧发一次诊断帧(1~10) | 1(DMA)/2(阻塞版) |

**`tele 1` 与 `tele 2` 互斥**:两者共占同一条 9600 链路,同时发必超预算。诊断期间用 `tele 2`,要看 VOFA+ 波形时切回 `tele 1`。
已有命令(`kp/kp2/kd/kd2/sp_kp/sp_ki/spd/zd/dd/disr/disl/yr/yl/ystra/ysel/get`)语义与行为**完全不变**。

### 4.7 与 ASCII 回复混流

`OK kp=450`、`get` 回显等 ASCII 回复会插进诊断字节流中间 → 上位机表现为偶发校验失败帧,**自动丢弃并计数,属正常**。发 `get`(9 行≈135ms)期间连续几帧会坏,报告里会有标注。

## 五、车端实现

### 5.1 新模块 `HARDWARE/hc-05/ble_diag.c / ble_diag.h`(新文件,UTF-8)

```
Diag_Init()                       初始化(阶段3加DMA配置)
Diag_Tick(servo_pwm, pid_select, valid_couter, danbian_flag)
    ① 按当前 tele 模式取数 → 组帧 → 发(阻塞或DMA)
    ② 其余 22 个字段从全局变量直接读
Diag_Command(line)                供 ble_tune.c 挂接 tele/rate 命令
```

- 帧缓冲静态 57B(≈零 RAM 开销,不需要黑匣子/环形缓冲)
- 字段表用 `static const` 结构体数组描述(指针 + 定标),**加字段=加一行**,模块化
- 只读全局,不写任何控制量

### 5.2 接线点(改动最小化)

| 文件 | 改动 | 行数 |
|---|---|---|
| `USER/main.c` | 遥测调用处([main.c:474](USER/main.c#L474))改为 `Diag_Tick(servo_pwm, pid_select, valid_couter, danbian_flag);` | 1 行 |
| `USER/main.c` | 头文件区 `#include "ble_diag.h"` | 1 行 |
| `HARDWARE/hc-05/ble_tune.c` | `Tune_ApplyOne` 开头挂 `if (Diag_Command(line)) return;` | 2 行 |

**不动**:雷达接收、电机闭环、舵机驱动、`bsp_bluetooth.c`、`CENTRE_LINE.c`、BLE 现有命令。

### 5.3 分阶段发送实现

- **阶段 1(阻塞降频版)**:沿用 `BLE_Send_Bit` 逐字节发,`rate` 默认 2(4.4 帧/秒,平均 30ms 阻塞/帧)

## 十、附:为什么不做黑匣子

原考虑用环形缓冲记录全量再 `dump`。int16 编码后 26 个量每帧只要 57B,9600 就装得下**实时全量流**,黑匣子(以及配套的 RAM 开销、dump 命令、停车导出流程)全部不必需。若将来字段继续膨胀到 >75B/帧,再启用黑匣子作为补充。
