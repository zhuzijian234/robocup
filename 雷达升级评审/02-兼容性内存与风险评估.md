配套：[实施方案](01-雷达升级详细实施方案.md)、[资料与验收](03-资料依据与验收清单.md)。  
证据等级：**A=本次源码/构建直接确认，B=官方或随设备资料，C=计算/设计预估，D=需实物验证。** C和D不能写成实测结果。

## 1. F407ZGT6能否完全兼容F407VET6例程？

**处理器和相关外设具备移植兼容性；芯片封装、开发板接线、软件工程和整车行为不能称为完全兼容。**

| 项目 | F407VET6 | F407ZGT6 | 对本次升级的意义 |
|---|---|---|---|
| 内核/最高频率 | Cortex-M4F、168 MHz | 相同 | 不是算力升级 |
| Flash | 512 KiB | 1024 KiB | ZG代码存储更大 |
| 普通SRAM | 112+16=128 KiB | 相同 | DMA可用片内SRAM没有因ZG而增加 |
| CCM数据RAM | 64 KiB | 相同 | CPU可用，DMA不可用 |
| 后备SRAM | 4 KiB | 相同 | 不并入常规点云预算 |
| 封装 | LQFP100 | LQFP144 | 不是引脚对引脚替换，板上排针位置不通用 |
| UART/定时器/DMA相关资源 | F407系列资源 | 对应资源可用 | 按GPIO名/复用/DMA映射迁移 |
| 软件库 | 示例HAL | 当前小车标准外设库 | 保留小车库，重写接入层 |

芯片容量、封装编码与内核依据[ST数据手册DS8626](https://www.st.com/resource/en/datasheet/stm32f407zg.pdf)及[STM32F407VE产品页](https://www.st.com/en/microcontrollers-microprocessors/stm32f407ve.html)、[STM32F407ZG产品页](https://www.st.com/en/microcontrollers-microprocessors/stm32f407zg.html)。总RAM包含CCM，不能理解成192 KiB连续DMA内存。

内存映射、CCM仅CPU访问和DMA映射依据[ST参考手册RM0090](https://www.st.com/resource/en/reference_manual/DM00031020.pdf)，重点核对F405/407章节，不能误用同手册F427/429的额外SRAM3。

### 1.1 当前工程配置存在实际差异（A）

`USER/Template.uvprojx:17`仍为STM32F407VETx；Flash驱动与范围也是512 KiB。两份EIDE只启用0x20000000的0x20000 RAM，CCM未启用。

含义：
- 在ZG上使用VE范围的固件可能正常运行，但不能证明板卡接线一致。
- 当前工程没有自动使用ZG的全部1 MiB Flash；改目标、烧录算法及三份构建配置时需一致。
- 不能直接将示例car.hex烧入小车验证兼容性：示例只做串口接收/打印，且初始化/引脚/控制均不同。
- 不能仅用DBGMCU同系列Device ID确认具体封装。以丝印、板卡资料和Flash容量信息共同确认。

### 1.2 具体串口兼容性（B+C）

推荐USART2_RX=PA3、AF7，DMA1 Stream5 Channel4；示例UART5_RX=PD2、AF8，其DMA映射为DMA1 Stream0 Channel4。接收型号不决定必须使用哪个UART。映射见[RM0090 DMA请求表](https://www.st.com/resource/en/reference_manual/DM00031020.pdf)。

若实际PCLK1=42 MHz、OVER8=0，按BRR最接近值计算：

| 请求波特率 | BRR | 实际波特率 | 分频误差 |
|---|---:|---:|---:|
| 230400 | 0x00B6 | 230769.23 | +0.1603% |
| 460800 | 0x005B | 461538.46 | +0.1603% |
| 512000 | 0x0052 | 512195.12 | +0.0381% |

计算说明：OVER16时有效分频值即BRR编码对应的整数，baud=PCLK/BRR。以上是本项目时钟假设下的计算，不是示波器测量；最终检查RCC、BRR读回以及TX/RX位宽。分频误差小不代表长线、电源干扰和雷达端时钟误差全部无风险。无必要为了512000专门改变全局PLL。

## 2. 内存是否充足？

使用本机Keil ARM Compiler 5、Cortex-M4.fp.sp、C99、O0、MicroLIB和分函数段；从当前uvproj读取55个C/汇编源文件、include及宏，使用现有EIDE生成scatter。编译/链接成功，0错误、44条警告。

| 项目 | 字节 | KiB |
|---|---:|---:|
| 当前RW+ZI及链接区域内填充/栈 | 58,216 | 56.85 |
| 当前ROM总计 | 29,892 | 29.19 |
| 普通SRAM容量 | 131,072 | 128 |
| 当前普通SRAM未占区域 | 72,856 | 71.15 |

证据：[构建摘要](当前工程构建摘要.json)、[完整map](../tmp/radar_upgrade_v3/current_build/baseline.map)、[编译命令与日志](../tmp/radar_upgrade_v3/current_build/build_review.json)、[源文件摘要](../tmp/radar_upgrade_v3/current_build/source_hashes.json)、[复现脚本](../tmp/radar_upgrade_v3/build_current.py)。

这是明确编译配置下的基线，不等于所有IDE入口已自动一致；也不证明运行正确。44条警告主要为未用变量、浮点转换和测试源字符编码，需要实施时整理。未因只改方案而修改固件。

### 2.2 为什么不能全局把800改成2048（A+C）

当前点云数组：3份N点、9份N/2点、3份200点，每项8 B，总计：
`60N + 4800 B`。

| N | 这些数组占用 | 后果 |
|---|---:|---|
| 800 | 52,800 B | 当前规模 |
| 1680 | 105,600 B | 仅算法数组已占大部分普通SRAM |
| 2048 | 127,680 B | 再加串口、栈和其他全局量会超128 KiB |

原始扫描容量与算法工作集必须分开。2048点原始扫描用紧凑8 B结构，算法仍最多720个角度格，保留旧800数组容量，后续才根据生命周期合并重复数组。

### 2.3 主推荐方案逐项预算（C）

| 项目 | 字节 |
|---|---:|
| 当前基线 | 58,216 |
| 删除两份旧1798 B接收缓冲 | −3,596 |
| 新循环DMA缓冲 | +1,024 |
| 软件字节FIFO | +8,192 |
| 两份2048×8 B原始扫描 | +32,768 |
| 小计 | **96,604** |
| 720×uint16角度索引 | +1,440 |
| 720字节有效标记 | +720 |
| 遥测模块总增量预算（含TX池等） | +2,816 |
| 雷达协议暂存区 | +512 |
| 扫描元数据 | +256 |
| 雷达统计、状态 | +512 |
| 栈由1024提高到4096的增量 | +3,072 |
| 堆预留 | +512 |
| 对齐及后续变更余量 | +2,448 |
| **预计总量** | **108,892 B = 106.34 KiB** |
| **距128 KiB剩余** | **22,180 B = 21.66 KiB，约16.92%** |

新增后半部分合计12,288 B，较上一版8 KiB预留更保守。4 KiB栈只是初始配置，必须静态调用链与实测水位确认；当前启动源码声明512 B堆，但本次map未保留HEAP段，因此单独再预留512 B，不把未链接的堆当已占空间。运行时大数组禁止放栈，不依赖动态分配保存扫描。

这里的“剩余21.66 KiB”不是已测峰值空闲，而是按预算计算的未分配容量。所有遥测扩展、扫描统计、临时复制必须从预算中扣除；不能重复加“几KB小缓存”而不更新表。

### 2.4 方案边界

| 配置 | 估计总RAM | 剩余 | 结论 |
|---|---:|---:|---|
| M10专用双1024点 | 90.34 KiB | 37.66 KiB | 仅实际最大点数确认后可选；1008槽名义值离1024很近 |
| 两型号共用双2048点 | 106.34 KiB | 21.66 KiB | 主方案 |
| M10P三份2048点 | 122.34 KiB | 5.66 KiB | 余量不足，不作为首版 |
| 谢露规划版原历史基线100,968 B直接叠加主方案增量 | 148.09 KiB | 超20,572 B | 不能直接复制主方案缓存；先裁剪数组或明确CCM布局 |

谢露版数值是历史map推算，本次未重新构建该分支，不当当前精确占用。

发布门槛建议：新map普通SRAM总占≤112 KiB，保留至少16 KiB未分配空间；若栈水位证明4 KiB不足，先增加栈并重新核算，再优化工作集。Flash目前仅约29.19 KiB，容量不是已识别瓶颈，但新增驱动/库后的最终大小仍需链接检查。不能把示例和现有工程两个map直接相加推算，因为库裁剪和重复符号不同。

### 2.5 CCM何时可用？

首版不依赖它。后续内存紧张时，CPU独占的拟合/中间数组可显式放CCM；雷达DMA缓冲必须在普通SRAM，未来任何DMA读取的数据也必须可达。使用命名section和明确scatter，不使用两个RAM区通配.ANY让DMA对象任意落位。

核对CCM时钟、初始化/清零、调试器加载和map地址。栈放CCM需另评估库函数/驱动是否把栈对象交给DMA。不能简单把0x20000000区域延长到0x30000，地址0x20020000不等于F407的CCM。

## 3. 数据率与CPU风险

### 3.1 数据负载是可以计算的，CPU性能必须测量

| 雷达 | 名义估算数据流 | 线路上限（8N1） | 说明 |
|---|---:|---:|---|
| LD14P | 4000/12×47≈15,667 B/s | 23,040 B/s | 每块1798 B不是完整圈 |
| M10 10 Hz | 10,000/42×92≈21,905 B/s；24包×10×92=22,080 B/s | 46,080 B/s | 标称点率与固定槽估算略有差异 |
| M10P 12 Hz | 20,000/70×160≈45,714 B/s；24包×12×160=46,080 B/s | 51,200 B/s | 后者约90%线路容量 |

按24扇区估算，M10P每圈1680槽，而20k/12≈1667点；容量取固定槽上界及余量，控制以实际角度/时间组圈。M10 20 Hz不按10 Hz表外推，协议行为待抓包确认。

示例逐字节中断在M10P名义数据流下约4.6万次/s；半块DMA约90次/s（满线约100次/s）。这解释了为什么选DMA，但不能据此宣称整个控制CPU占用必然很低：三角函数、拟合、双重遍历、printf和蓝牙都会耗时。

### 3.2 压力目标（C，非实测）

- 最坏DMA中断延迟加拷贝时间必须明显小于10 ms；建议目标≤1 ms并记录峰值。
- 满线8192 B约160 ms只是字节队列容量。以75%（6144 B）为调查阈值，持续上涨立即定位消费者耗时，不等待真正满。
- 12 Hz时解析＋感知＋控制的最坏预算建议<41.7 ms（半圈周期）；10 Hz时<50 ms。若目标车速要求更短，以实际允许延迟为准。
- 独立记录包接收、整圈年龄、处理时间、控制周期和输出时刻。单看平均帧率不足以验收。
- ISR无打印/浮点大循环；蓝牙使用完整消息TXE队列；相同日志不同编译优化级别需要重新验证，不把切O2当未经验证的万能修复。

## 5. 对小车的可能负影响与收益边界

如果按方案接入并通过门槛，额外数据负担可控制在F407资源内；仍可能因安装、回波分布、控制周期变化而需要标定。不能保证换雷达即提升圈速。

新雷达看见更多点时，也可能看见更多管缝后的背景；高反标志是辅助信息，不是“铝管应全部滤除”的依据。角度更密主要有利于代表点选择和几何稳定性，首版算法仍按0.5°/1°取样，不能把原始点率翻倍直接换算成算法精度翻倍。

低速同条件比较漏弯、假断点、碰撞/脱轨、摆动、感知年龄和完成时间。如果旧雷达已满足近场稳定性，升级收益可能有限；若故障源是现有解析/控制问题，单换硬件也不会消失。

**资源结论：主方案的Flash空间充足，普通SRAM有预算余量；不需要因M10P而立刻换更强主控。但“完全兼容”和“比赛更稳”都必须由实物与整车验收确认。**
